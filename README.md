# Evidence-Grounded Clinical RAG System (Research Prototype)

> ⚠️ **Research / demo prototype. Not a medical device.** All patient data is
> synthetic. Answers are generated by an AI model and independently
> verified against retrieved evidence, but may still be incomplete or
> wrong. This system does not diagnose, treat, or provide medical advice,
> and must never be used for real clinical decisions.

## 1. Problem & Motivation

LLMs can produce fluent, confident-sounding medical text that is not
actually grounded in real evidence - a serious risk in any healthcare
context. This project is a research prototype that asks:

> **Can hybrid retrieval + reranking + claim-level verification improve the
> factual reliability and citation grounding of LLM-generated healthcare
> responses?**

It builds a full pipeline - hybrid (BM25 + dense) retrieval over real PubMed
literature, cross-encoder reranking, patient-aware query construction, LLM
generation with mandatory citations, claim extraction, independent
NLI-based claim verification, citation verification, and a reliability
gate - and then **measures** (not assumes) how well that pipeline actually
does at reducing hallucinated/unsupported clinical claims, using a
reproducible benchmark, baselines, and an ablation study. See
[`RESULTS.md`](RESULTS.md) for the measured numbers.

## 2. Architecture

```
PubMed (real abstracts, live-fetched + locally cached)
        -> ingestion (parse / clean / section-aware chunk)
        -> BM25 index (rank_bm25)  +  Dense index (FAISS + PubMedBERT sentence-transformers)
        -> Hybrid fusion (configurable weighted or RRF)
        -> Cross-encoder reranker (MedCPT-Cross-Encoder)
        -> Top-K evidence
                |
Patient (synthetic labs/meds/history) -> patient-aware query construction (embedding-similarity field selection)
                |
        -> LLM generation (local HF model or any OpenAI-compatible API) with mandatory [E#] citations
        -> Claim extraction (sentence + citation-marker parsing)
        -> Claim verification (NLI entailment model + optional LLM secondary verifier)
        -> Citation verification (traces every [E#] back to an actually-retrieved chunk)
        -> Reliability gate (flag / remove / rewrite unsupported or contradicted claims)
        -> Final answer + per-claim verification status
```

See `backend/pipeline.py` for the single orchestrator that wires every
stage together, used identically by the live API and by the evaluation
harness.


## 3. Installation

Requires Python 3.11+ and Node 18+. No GPU required (everything defaults to
CPU-friendly models).

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install --index-url https://download.pytorch.org/whl/cpu torch==2.4.1
pip install -r requirements.txt

cd frontend && npm install && cd ..
```

Copy `.env.example` to `.env` if you want to change any defaults (an
OpenAI-compatible API key, a different embedding/reranker model, etc.) -
**none of this is required to run the system**; the defaults use a local
Hugging Face model and no external API keys.

## 4. Dataset setup

The evidence corpus is real, public PubMed abstracts fetched via NCBI
E-utilities, covering the conditions present in the synthetic patients
(type 2 diabetes, hypertension, hyperlipidemia, thyroid disease, anemia,
chronic kidney disease). No papers/PMIDs/DOIs are ever fabricated - only
what NCBI actually returns.

```bash
# Fetches ~18 topic queries from PubMed and caches them to data/raw/pubmed/*.json,
# then chunks everything into data/processed/chunks.jsonl
python -m backend.scripts.build_corpus

# Rebuild later purely from the local cache, with no network access at all
# (this is the documented offline fallback path):
python -m backend.scripts.build_corpus --offline

# Build the BM25 + FAISS dense indices from the chunked corpus
python -m backend.scripts.build_index
```

Synthetic patients live in `data/patients/*.json` (3 patients covering
diabetes, hypertension+CKD, and thyroid/anemia profiles). The evaluation
benchmark lives in `data/evaluation/benchmark.json` - each item's
`gold_evidence` chunk IDs were identified by actually running retrieval
against the built index and inspecting the real returned passages, not
guessed.

## 5. Running the application

One-command dev startup (runs both, Ctrl+C stops both):

```bash
./scripts/dev.sh
```

Or run each side separately:

```bash
# Terminal 1 - backend
source .venv/bin/activate
uvicorn backend.main:app --reload --port 8000

# Terminal 2 - frontend
cd frontend && npm run dev
```

Open http://localhost:5173. Select a synthetic patient, ask a question
(or pick an example), and inspect the retrieval panel (BM25 / dense / fused
/ reranked tabs), the generated answer with inline `[E#]` citations, and the
per-claim ✓ Supported / ⚠ Unsupported / ✗ Contradicted verification status.
The "Research Dashboard" tab surfaces whatever evaluation results have been
generated (see below).

### Example queries

- "What could explain my recent HbA1c result?"
- "What are common gastrointestinal side effects of my metformin?"
- "How does my declining kidney function relate to my blood pressure medication?"
- "What do my thyroid labs mean?"

## 6. Running evaluation

```bash
# Baselines: LLM-only, Dense+LLM, BM25+LLM, Hybrid+LLM, Final System
python -m backend.evaluation.baselines

# Ablation: Full System minus BM25 / dense / reranker / claim verification / patient context
python -m backend.evaluation.ablation
```

Both commands run the real pipeline over every item in
`data/evaluation/benchmark.json` for each configuration and write measured
results to `experiments/results/*.json` (one file per canonical
configuration, plus `baselines_summary.json` / `ablation_summary.json`).
Runs are cached per-configuration (pass `--force` to re-run), which makes
long CPU-only evaluation runs resumable. The FastAPI `/api/dashboard`
endpoint (and the frontend Dashboard tab) simply reads whatever is in
`experiments/results/` - nothing is fabricated if you haven't run the
commands above yet.

## 7. Results

Measured on the 15-item benchmark with the default local LLM
(`Qwen2.5-1.5B-Instruct`, CPU): the final system reaches **66.7% Recall@5**
(vs. an 81% target) - 2.5-4x better than any non-reranked baseline, the
clearest validated result in this study - but citation accuracy (14.3%),
supported-claim rate (1.2%), and hallucination rate (98.8%) fall well short
of their targets (85% / 82% / ≤13%). Investigation traced this primarily to
the small local generator's compound claim phrasing interacting poorly with
strict NLI entailment scoring against short retrieved chunks, not to
retrieval quality. The ablation study also surfaced a genuine design
weakness: removing patient-context augmentation from the retrieval query
*improves* Recall@5 to a perfect 100% (from 66.7%), suggesting the current
query-construction approach dilutes retrieval signal rather than helping
it - see `RESULTS.md` Future Work for the proposed fix. See
[`RESULTS.md`](RESULTS.md) for full methodology, the baseline/ablation
tables, concrete failure cases (including the no-retrieval baseline
fabricating citation markers that the verifier caught
100% of), and next steps - the single highest-leverage one being to re-run
against a stronger generator via the OpenAI-compatible provider.

## 8. Limitations (see RESULTS.md for detail)

- Small (~1,000-chunk) corpus built from ~18 topic queries - not
  comprehensive biomedical coverage.
- No off-the-shelf biomedical-specific NLI model is readily available; claim
  verification uses a strong general-purpose NLI model instead, documented
  as a practical compromise.
- The default local LLM is a small (1.5B parameter) CPU-friendly model,
  chosen so the system runs with zero API keys - swapping in a stronger
  model via the OpenAI-compatible provider (`.env`: `LLM_PROVIDER=openai`)
  is a one-line config change and may materially change the measured
  numbers.
- This is a research prototype for studying retrieval/verification
  architecture, not a validated clinical tool.
